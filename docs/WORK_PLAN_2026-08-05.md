## Phase 2 — Wire the real progress endpoint into the upload page

**Problem.** `_app.upload.tsx:135` fakes progress:

```ts
const tick = window.setInterval(() => setStage((s) => (s < 8 ? s + 1 : s)), 400);
```

Nine stages at 400 ms = **3.6 seconds of animation** in front of an operation the handbook
measures at **11 minutes** (`fir-65-2024`) to **49 minutes** (`FIR-0006-2025 U`). The bar
fills, then sits at "Stage 8/9" for the remaining 48 minutes with no further signal. A user
cannot distinguish that from a hang.

The backend has served real progress since 3 Aug and nothing consumes it:
`GET /v1/analyze/progress/{ds}?window=` returns `stage`, `stage_label`, `percent`,
`eta_seconds`, `elapsed_seconds`, `message`, `status`, and the `stages` array with weights.

### Changes

| File | Change |
|---|---|
| `frontend/src/lib/api.ts` | add `analyzeProgress(dataset, window)` + `AnalyzeProgress` type mirroring `analyze_progress.STAGES` |
| `frontend/src/hooks/use-analyze-progress.ts` | **new** — polls every 1.5 s while running, stops on `done`/`error`/unmount |
| `frontend/src/routes/_app.upload.tsx` | drive the stage strip from the server's 9 stages; show percent, elapsed and ETA; delete the fake ticker |

### Design decisions, taken up front

1. **Server stage list is authoritative.** The page currently hardcodes its own nine labels
   (`"Ingest", "Normalize", …`) which do not match the server's
   (`"Parsing evidence files", …`). Two lists that must agree and have no test tying them
   together will drift. The response carries `stages`; render that, and fall back to the
   local list only before the first poll returns.
2. **Poll interval 1.5 s.** The endpoint is a dict read behind a lock — cheap. But the
   pipeline is CPU-bound Python holding the GIL, so the API is *unresponsive* while it runs
   (handbook §6). Polls will therefore hang rather than fail; the hook must tolerate a slow
   or failed poll without tearing down.
3. **A failed poll is never fatal.** Progress is decoration. If the poll 500s or times out,
   keep the last known state and keep polling — never surface an error or abort the analyze.
4. **Do not poll when idle.** Only while `running` is true, so no background traffic.

**Must not break:** the analyze call itself, the upload flow, the fixture-dataset guard on
`demo`/`smoke`, or the `finally { clearInterval }` fix already recorded in that file's
comments.

**Verify:** `tsc` clean, `vitest` green, and drive it in a browser against `demo` —
the one thing `GAPS.md` §4 says has never been done.

## Phase 3 — Re-run button and "loaded from cache" badge

**Problem.** `POST /v1/analyze` accepts `force: bool` and returns `from_cache: bool`. The
frontend sends neither and reads neither, so:

- an analyst cannot tell a **fresh 49-minute run** from a **130 ms cache hit** — the same
  toast appears for both;
- once a snapshot exists there is **no way to re-run** from the UI. After changing a
  profile or a threshold, the stale snapshot is served indefinitely.

The second is the more serious: it makes the tool silently show old figures after a config
change, which is the class of failure `CLAUDE.md` rule 5 exists to prevent.

### Changes

| File | Change |
|---|---|
| `frontend/src/lib/api.ts` | `analyze(..., opts?: { persist?, force? })`; surface `from_cache` on the response type |
| `frontend/src/routes/_app.upload.tsx` | "Re-run" button (only once a result exists), cache badge on the result line, confirm before forcing |

**Confirm before forcing.** A forced run on a real case costs 11–49 minutes of CPU and
deletes the existing snapshot first. A misclick must not be able to do that silently.

**Must not break:** the default path stays `force: false`, so existing callers and tests are
unaffected. `persist` keeps its current meaning and position.

From `docs/handbook/GAPS.md` §6, each of which looks like easy value and is not:

- **FR-9 STRONG = 0.** The IPDR covers 19 phones of 4,026. Every code-side hypothesis has
  been built and measured and none moved it. It is an exhibit request to the case officer.
- **New parser profiles for FR-4.** The genuine unread gap across both real cases is
  **3 tables / 92 rows = 0.008%** of 1,114,168 rows.

  looks like free coverage; one of them holds cell IDs, one of which is 15 digits and passes

  that cell.

here. Phases 2 and 3 are frontend-only; Phase 1 is documentation only.
